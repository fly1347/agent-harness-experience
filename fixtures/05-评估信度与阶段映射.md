# RAG评估知识系统-05-评估信度与阶段映射

## 1. 为什么要讨论评估信度

RAG 评估不是只要有指标、有工具、有分数就完成了。

评估本身也需要被判断。

因为评估过程可能受到很多因素影响：

```text id="57zxvt"
问题集是否有代表性；
expected evidence 是否准确；
参考答案是否可靠；
评估模型是否稳定；
指标是否适合当前任务；
人工判断是否一致；
同一实验是否可复跑；
不同 run 是否可比较。
```

如果评估本身不稳定，后续实验结论也会不稳定。

例如：

```text id="1k8zfl"
系统没有变化，但评估模型分数波动；
答案质量差不多，但不同 judge 给出不同结论；
问题集太小，平均分被少数题目影响；
reference 本身不完整，导致正确答案被误判；
指标只看相关性，却被用来证明正确性。
```

因此，RAG 工程评估不仅要关心系统质量，也要关心评估质量。

---

## 2. 信度与效度

评估质量可以从两个基本概念理解：

```text id="2hcos5"
信度：评估结果是否稳定。
效度：评估是否真的测到了想测的东西。
```

### 2.1 信度

信度关注稳定性。

它回答：

```text id="17furb"
同一个系统、同一批问题、同一个评估口径下，结果是否相对一致？
```

影响信度的因素包括：

```text id="dmrzwd"
LLM judge 波动；
模型版本变化；
temperature 设置；
评估 prompt 变化；
运行超时；
抽样题目过少；
人工标注口径不一致。
```

信度低时，评估结果不适合做强结论。

例如：

```text id="l69hjx"
一次 run 中 answer_relevancy 提升 0.02，
但评估模型本身波动可能超过这个幅度，
此时不应该直接说系统明显变好。
```

### 2.2 效度

效度关注指标是否测对了对象。

它回答：

```text id="mx2v3s"
这个指标是否真的反映了我想判断的能力？
```

例如：

```text id="nqa2w9"
faithfulness 测答案是否被上下文支撑，
但不能单独证明答案完整。

answer_relevancy 测答案是否回应问题，
但不能单独证明答案事实正确。

context_precision 测检索上下文中有效材料是否靠前，
但不能单独证明最终答案质量。

citation_count 测引用数量，
但不能证明引用真的支撑结论。
```

效度不足时，指标容易被误用。

所以评估结论要写清楚：

```text id="f9eglv"
这个指标看什么；
不看什么；
能支持什么结论；
不能支持什么结论。
```

## 3. LLM Judge 的不稳定性

LLM judge 是 RAG 评估中常用方法。

它可以帮助判断：

```text id="lg8uub"
答案是否忠实；
答案是否相关；
证据是否充分；
引用是否支撑；
拒答是否合理。
```

它的优势是：

```text id="09wt2l"
可以批量评估；
可以处理语义判断；
可以减少纯人工成本；
可以用统一 rubric 做初筛。
```

但它也有明显限制：

```text id="m35te6"
不同模型判断标准不同；
同一模型不同版本可能变化；
长答案和复杂问题更容易误判；
中文工程问题可能受语言理解影响；
评估 prompt 写法会影响结论；
低成本模型可能更不稳定；
模型可能偏好某种表达风格。
```

因此，LLM judge 的结果应被视为：

```text id="jji7r8"
自动化辅助判断
```

而不是绝对真值。

## 4. 评估模型选择

评估模型选择会影响分数。

常见选择维度包括：

```text id="gkhjcb"
理解能力；
中文能力；
专业领域理解；
稳定性；
成本；
速度；
上下文长度；
结构化输出能力；
版本可控性。
```

更强的评估模型通常更可靠，但成本更高。

更便宜的模型适合批量初筛，但关键结论需要抽查。

可以采用分层策略：

```text id="dsli9z"
低成本模型：批量跑全量回归集；
强模型：复核关键失败或争议样本；
人工检查：确认代表性结论和公开展示材料。
```

这种策略能平衡成本和可信度。

## 5. 人工抽查的作用

人工抽查不是为了替代自动评估。

它的作用是校准和兜底。

适合人工抽查的场景包括：

```text id="lsfx3o"
评估模型分数异常；
不同 judge 结论冲突；
关键指标发生明显变化；
代表性题目从 pass 变 fail；
准备进入阶段总结或公开展示；
引用支撑关系比较复杂；
拒答边界不清；
多文档综合题需要判断完整性。
```

人工抽查重点看：

```text id="oirnhc"
答案是否真的解决问题；
证据是否充分；
引用是否支撑；
失败归因是否合理；
评估模型是否误判；
结论是否可以公开表达。
```

人工抽查成本高，所以不需要覆盖所有题。

更合理的方式是：

```text id="xjcrwu"
全量自动评估；
抽样人工复核；
重点失败样本人工检查；
关键结论人工确认。
```

## 6. Rubric 的作用

Rubric 是评分规则。

它把“答案好不好”拆成明确维度。

例如，一个多文档综合题的 rubric 可以包括：

```text id="kn7lrx"
是否覆盖所有必要来源；
是否区分不同来源观点；
是否说明限制条件；
是否避免无证据扩写；
是否给出可追溯引用；
是否结构清楚。
```

Rubric 的价值是：

```text id="61n61r"
降低主观判断；
让人工和 LLM judge 有共同标准；
方便复查；
方便比较不同 run；
方便公开解释评估口径。
```

Rubric 尤其适合：

```text id="2fm2b8"
答案完整性；
对比题；
流程题；
多文档综合题；
拒答边界；
引用支撑。
```

没有 rubric 时，质量评估容易变成泛泛判断。

有 rubric 后，评估结论会更可解释。

## 7. 问题集对信度的影响

评估结果不仅取决于模型和指标，也取决于问题集。

问题集太小，结果容易不稳定。

问题集太单一，无法覆盖系统能力。

问题集太难，可能全部失败，无法区分改动效果。

问题集太简单，可能全部通过，无法发现问题。

一个更稳的问题集应该覆盖：

```text id="i7weqw"
简单事实；
概念解释；
流程问题；
对比问题；
多文档综合；
知识库外问题；
证据不足问题；
易混问题；
引用检查；
权限或安全边界。
```

问题集还要记录：

```text id="wj2tze"
question_id；
question_type；
expected_behavior；
expected_evidence；
difficulty；
notes；
version。
```

如果问题集发生变化，评估结果不能直接和旧 run 比较。

因此，报告中要记录：

```text id="pml7lq"
question_set_version
```

## 8. Reference 与 Expected Evidence 的可靠性

RAG 评估常常需要 reference 或 expected evidence。

它们本身也会影响评估质量。

### 8.1 Reference

Reference 是参考答案或标准答案。

它影响：

```text id="9yo7yc"
answer_correctness；
context precision；
context recall；
部分 LLM judge 判断。
```

Reference 的问题包括：

```text id="uk6xzc"
参考答案不完整；
参考答案过于理想化；
参考答案和知识库内容不一致；
参考答案由 AI 生成，未经人工确认；
参考答案只覆盖一种表达方式。
```

### 8.2 Expected Evidence

Expected evidence 是预期证据。

它影响：

```text id="rt89zg"
any_hit；
full_hit；
source_level_hit；
chunk_level_hit；
evidence coverage。
```

Expected evidence 的问题包括：

```text id="y5hdoa"
source 级较粗；
chunk 级标注成本高；
切分策略变化后 chunk_id 变化；
同一问题可能有多个可用证据路径；
人工标注可能遗漏证据。
```

因此，项目里要明确 expected evidence 的粒度。

常见策略是：

```text id="gqx2kq"
source 级用于基础回归；
chunk 级用于重点问题；
answer-bearing chunk 用于典型失败诊断；
人工抽查用于确认关键样本。
```

## 9. 分数解释原则

评估分数要谨慎解释。

可以遵循几个原则。

### 9.1 不单看一次分数

单次分数只能说明当前 run 的状态。

更重要的是：

```text id="wr9758"
同一批问题下，和 baseline 比有什么变化。
```

### 9.2 不单看平均分

平均分可能掩盖关键失败。

要同时看：

```text id="65rndr"
逐题结果；
pass / fail；
失败类型；
关键题变化；
问题类型分布。
```

### 9.3 不把一个指标解释成所有质量

例如：

```text id="lw8xk9"
faithfulness 高，不等于答案完整；
answer_relevancy 高，不等于事实正确；
citation_count 高，不等于引用有效；
any_hit 高，不等于证据充分。
```

### 9.4 小幅变化不急着下结论

如果分数变化很小，需要考虑：

```text id="l8qipq"
评估模型波动；
样本量；
运行随机性；
人工抽查结果；
逐题变化是否一致。
```

### 9.5 工程结论要同时写收益和代价

例如：

```text id="q6p78t"
检索命中率提升；
但延迟上升；
引用稳定性没有变化；
拒答题出现回归；
因此该改动需要继续观察。
```

## 10. 阶段映射总览

评估体系要回到项目阶段。

本项目阶段顺序为：

```text id="67n9yx"
A（基线）
→ A’（最小评估）
→ B（评估闭环）
→ D-lite（双步检索 + 证据充分性检查）
→ C（服务化 / UI / Docker / 压测 / 观测）
→ C+（模型认知与选型 / 成本与部署认知）
→ D-full（完整工作流）
→ E（企业化）
→ F（整理发布）
```

每个阶段的评估重点不同。

---

## 11. Phase A：基线阶段

A 阶段的评估目标是：

```text id="c8do6t"
确认 RAG 主链路能跑通。
```

关注点包括：

```text id="m4jip8"
资料能进入系统；
检索能返回结果；
模型能生成答案；
答案能带引用；
知识库外问题能拒答；
运行过程能留下基础记录。
```

适合的评估方式：

```text id="yhqw8z"
最小问题集；
人工检查；
基础 pass / fail；
citation 数量检查；
知识外拒答检查。
```

A 阶段不需要复杂指标。

它更像阶段验收。

核心是：

```text id="h8b3wx"
系统从无到有，主链路闭合。
```

---

## 12. Phase A’：最小评估阶段

A’ 阶段的评估目标是：

```text id="iqo79v"
让主链路能被最小评估。
```

关注点包括：

```text id="1f31y8"
固定问题集；
expected_behavior；
expected_evidence；
批量运行；
逐题记录；
基础命中；
基础引用；
初步失败记录。
```

适合的评估方式：

```text id="mi53va"
10 题最小回归集；
per-question report；
summary report；
人工抽查。
```

A’ 的价值是建立评估入口。

从这一阶段开始，系统改动就可以被复跑和比较。

---

## 13. Phase B：评估闭环阶段

B 阶段的评估目标是：

```text id="4fbavw"
形成批量回归和指标观察能力。
```

关注点包括：

```text id="5r94wo"
问题集扩展；
RAGAS 指标；
检索命中；
生成质量；
不同实验对比；
评估结果记录；
失败归因初步形成。
```

适合的评估方式：

```text id="v1kza1"
扩展回归集；
baseline vs experiment；
RAGAS；
summary report；
compare report；
逐题失败分析。
```

B 阶段是评估闭环真正成形的阶段。

它的重点不是某个指标多高，而是：

```text id="u322ol"
系统改动之后能被同一批问题反复验证。
```

---

## 14. Phase D-lite：双步检索与证据充分性

D-lite 阶段的评估目标是：

```text id="lijvlc"
让系统能判断证据是否足够，并在不足时补救或拒答。
```

关注点包括：

```text id="5laclo"
双步检索；
证据充分性；
missing evidence；
二次检索；
拒答；
source_hit_chunk_miss；
证据缺口。
```

适合的评估方式：

```text id="bfc8v6"
sufficiency verdict；
evidence packet；
missing evidence report；
拒答正确性；
检索与证据层失败归因。
```

D-lite 的核心是把 RAG 从“检索后直接生成”推进到：

```text id="wmcdlp"
生成前先判断证据够不够。
```

这是可控 RAG 的关键能力。

---

## 15. Phase C：服务化与观测阶段

C 阶段的评估目标是：

```text id="v9xuod"
确认系统能作为服务运行。
```

关注点包括：

```text id="y5ah2y"
API；
UI；
Docker；
压测；
日志；
metrics；
错误处理；
fallback；
延迟；
吞吐。
```

适合的评估方式：

```text id="1pfovl"
接口测试；
Docker 启动验证；
load test；
latency report；
error report；
metrics 检查。
```

C 阶段的评估对象从答案质量扩展到运行质量。

它回答：

```text id="tyahv8"
系统能不能被调用、部署、压测、观测。
```

## 16. Phase C+：模型、成本与部署认知

C+ 阶段的评估目标是：

```text id="l2iiwf"
理解模型选型、成本和部署约束。
```

关注点包括：

```text id="arfcbc"
本地模型；
API 模型；
评估模型；
生成质量；
延迟；
token；
调用成本；
部署可行性；
预算阈值。
```

适合的评估方式：

```text id="nsjq5v"
模型对比；
质量 / 成本 / 延迟三维比较；
cost ledger；
token 统计；
人工抽查。
```

C+ 的重点是建立成本意识和选型判断。

它不只问哪个模型效果好，还要问：

```text id="bju3ue"
这个效果是否值得它的成本和部署代价。
```

```text id="eicwv8"
让系统具备更完整的工作流判断和状态记录。
```

```text id="bso0sx"
EvidencePacket；
sufficiency judge；
workflow state；
trace；
failure_reason；
多步骤控制；
状态流转。
```

适合的评估方式：

```text id="ag53oz"
工作流通过率；
分类正确性；
证据包检查；
sufficiency 结果；
逐题 trace；
失败归因。
```

D-full 的核心是把 RAG 从单次问答推进到：

```text id="fvjaxp"
可控工作流。
```

它更关注状态、路径和决策过程。

```text id="82rj3l"
企业化基线。
```


```text id="g0541d"

release evidence pack；

README；
```

```text id="x4x5qh"
整理已有报告；

标注已知限制；
形成公开表达。
```

F 阶段不新增主链路能力。

```text id="9zklp6"
把已经做过的工程能力讲清楚、证据化、结构化。
```

## 20. 小结

评估信度决定结论是否可靠。

阶段映射决定评估体系如何落到项目演进。

整体来看：

```text id="v32z2a"
A / A’：从能跑到能被最小评估；
B：形成回归闭环；
D-lite：加入证据充分性；
C：进入服务化和观测；
C+：理解模型、成本、部署；
D-full：形成完整工作流；
E：补齐企业化控制面；
F：整理发布和证据收束。
```

一句话收束：

```text id="migdfb"
可靠的 RAG 评估，不只是有分数，而是能说明分数从哪里来、是否可信、对应哪个阶段目标、能支撑什么工程结论。
```
