# RAG评估知识系统-03-实验变量与回归集设计

## 1. 为什么评估需要实验设计

RAG 系统不是一次写完就固定不变。

实际开发中会不断调整：

```text id="fq9v1g"
语料；
切分；
embedding；
topk；
rerank；
prompt；
模型；
证据筛选；
引用绑定；
拒答策略；
成本控制。
```

每次调整都可能带来收益，也可能带来副作用。

例如：

```text id="f9c40a"
topk 增大，可能提高召回，也可能增加噪声和 token；
prompt 变严格，可能减少幻觉，也可能增加误拒答；
模型变强，可能提高答案质量，也可能增加成本和延迟；
rerank 加入后，可能改善排序，也可能让系统变慢。
```

因此，RAG 评估不能只看一次运行结果。

它需要实验设计。

实验设计的目标是：

```text id="uqtzdr"
在可控变量下，判断一次改动对系统效果、成本、延迟和稳定性的影响。
```

---

## 2. Baseline 与 Experiment

回归评估通常从 baseline 开始。

```text id="vl36pd"
baseline = 当前稳定版本；
experiment = 在 baseline 基础上做一个明确改动后的版本。
```

例如：

```text id="ieyifi"
baseline：topk=5；
experiment：topk=10。
```

或者：

```text id="ps20td"
baseline：无 rerank；
experiment：加入 rerank。
```

一次有效实验应该尽量只改一个主要变量。

这样才能判断结果变化来自哪里。

如果同时修改：

```text id="gvb9kw"
chunk_size
embedding
topk
prompt
model
```

结果即使变好，也很难知道是哪一项带来的提升。

因此，回归实验的基础原则是：

```text id="g3y7yp"
一次实验，一个主变量；
同一批问题，重复运行；
保留配置，保留结果；
用报告比较变化。
```

---

## 3. 回归集的作用

回归集是 RAG 评估闭环的核心。

它是一组固定问题，用来反复测试系统。

回归集回答的是：

```text id="oqcyrb"
系统改动之后，原来能答的问题是否还稳定；
原来答不好的问题是否变好；
是否引入新的失败；
指标变化是否可解释。
```

回归集不同于临时测试问题。

临时测试问题只能帮助开发者观察当前行为。

固定回归集则能形成对比。

它的价值在于：

```text id="pbtwyi"
每次改动都跑同一批题；
每次运行都保留结果；
每次结果都能和历史版本比较。
```

---

## 4. 回归集应该覆盖什么

一组可用的 RAG 回归集，应该覆盖不同问题类型。

常见类型包括：

```text id="jkbgpk"
简单事实题；
概念解释题；
流程题；
对比题；
多文档综合题；
边界题；
知识库外问题；
证据不足问题；
易混问题；
权限或安全相关问题。
```

不同问题类型考察不同能力。

| 问题类型   | 主要考察           |
| ------ | -------------- |
| 简单事实题  | 基础检索和答案生成      |
| 概念解释题  | 单源证据理解         |
| 流程题    | 结构化回答          |
| 对比题    | 多来源组织          |
| 多文档综合题 | 跨文档召回和证据覆盖     |
| 知识库外问题 | 拒答             |
| 证据不足问题 | sufficiency 判断 |
| 易混问题   | 检索噪声和模型分辨      |
| 权限问题   | ACL 和安全边界      |

回归集不一定一开始很大。

重点是：

```text id="ub7z4g"
题目有代表性；
预期行为清楚；
可以反复运行；
结果能解释。
```

## 5. 回归题目需要记录什么

每个问题最好包含结构化字段。

基础字段：

```text id="h142ct"
question_id
query
expected_behavior
expected_evidence
min_evidence_required
notes
```

扩展字段：

```text id="tbotip"
question_type
difficulty
expected_sources
expected_chunks
reference_answer
rubric
tags
acl_scope
```

其中最关键的是：

```text id="7x0s2v"
expected_behavior
expected_evidence
```

`expected_behavior` 说明系统应该做什么。

例如：

```text id="wklqe5"
answer：应该回答；
refuse：应该拒答；
ask_clarification：应该请求澄清；
partial_answer：只能部分回答并说明缺口。
```

`expected_evidence` 说明答案应该依赖哪些来源。

它可以先做到 source 级。

如果条件允许，再补充 chunk 级。

## 6. 回归集规模的演进

RAG 项目的回归集可以逐步扩展。

不需要一开始追求完整。

一个合理演进是：

```text id="ss64wx"
最小回归集
→ 扩展回归集
→ 专项回归集
→ 企业化回归集
```

### 6.1 最小回归集

目标是跑通评估闭环。

规模可以很小。

例如：

```text id="o7puyg"
10 题；
覆盖基础事实、概念解释、拒答、引用。
```

重点是：

```text id="y1h5ew"
能批量跑；
能保存结果；
能看出明显失败。
```

### 6.2 扩展回归集

目标是提高覆盖度。

例如：

```text id="xgaiqm"
30 题；
加入对比、多文档、边界题、易混题。
```

重点是：

```text id="kf9yec"
能看趋势；
能比较实验；
能发现不同问题类型的弱点。
```

### 6.3 专项回归集

目标是验证某个能力。

例如：

```text id="nxbhuj"
证据充分性专项；
拒答专项；
citation 专项；
权限专项；
安全注入专项；
成本专项。
```

重点是：

```text id="4m1qd1"
围绕一个能力集中施压。
```

### 6.4 企业化回归集

目标是验证上线约束。

例如：

```text id="g8321o"
不同用户权限；
敏感信息；
审计日志；
预算阈值；
fallback；
metrics。
```

重点是：

```text id="szj99r"
系统能不能稳定、可控、可审计。
```

## 7. 常见实验变量

RAG 的实验变量可以按层划分。

### 7.1 数据与建库变量

```text id="mffhug"
语料规模；
文档来源；
清洗规则；
loader；
chunk_size；
chunk_overlap；
标题保留；
表格处理；
embedding 模型；
embedding 维度；
向量库；
索引参数；
rebuild 策略。
```

这些变量主要影响：

```text id="vj65lg"
召回；
证据完整性；
chunk 可追溯；
索引稳定性；
检索延迟。
```

### 7.2 检索变量

```text id="kwfmmp"
topk；
score_threshold；
query rewrite；
hybrid search；
rerank；
metadata filter；
相邻片段扩展。
```

这些变量主要影响：

```text id="cg8f8y"
目标证据是否回来；
排序是否靠前；
噪声是否增加；
多来源是否覆盖。
```

### 7.3 证据变量

```text id="t2hmqm"
max_chunks_in_prompt；
context truncation；
evidence packet size；
sufficiency judge；
二次检索；
missing evidence 报告。
```

这些变量主要影响：

```text id="q4y7ip"
模型能看到多少证据；
证据是否足够；
是否正确拒答；
prompt token 是否增加。
```

### 7.4 生成变量

```text id="uc2arq"
prompt 模板；
模型；
temperature；
max_tokens；
答案结构；
拒答规则；
引用要求；
是否允许常识补充。
```

这些变量主要影响：

```text id="6bhcpd"
faithfulness；
answer relevancy；
完整性；
格式稳定性；
幻觉；
延迟；
成本。
```

### 7.5 系统与企业化变量

```text id="l336am"
API；
UI；
Docker；
并发；
缓存；
fallback；
ACL；
安全规则；
成本阈值；
审计字段；
metrics 导出。
```

这些变量主要影响：

```text id="6et40c"
服务稳定性；
吞吐；
延迟；
权限隔离；
安全拦截；
成本可控；
审计可追踪。
```

## 8. 观测出口

实验变量很多，但观测出口要收束。

一次 RAG 实验可以重点观察：

```text id="5bc2g8"
检索结果；
证据充分性；
最终答案；
引用；
延迟；
成本；
失败原因。
```

对应指标：

```text id="xineko"
any_hit / full_hit；
sufficiency_verdict；
faithfulness / answer_relevancy；
citation_coverage；
retrieval_ms / generation_ms / total_ms；
prompt_tokens / completion_tokens / estimated_cost；
failure_reason。
```

这些指标共同说明：

```text id="o1605v"
效果有没有变；
代价有没有变；
失败类型有没有变。
```

不要只看平均分。

回归评估还要看逐题变化。

## 9. Compare Report

Compare report 是回归评估的重要输出。

它用于比较两个 run：

```text id="22fxnp"
baseline_run
experiment_run
```

核心内容包括：

```text id="y057iu"
总体指标变化；
逐题 pass/fail 变化；
检索命中变化；
证据充分性变化；
生成质量变化；
引用变化；
延迟变化；
成本变化；
失败原因变化。
```

常见对比结果：

```text id="u2fe56"
pass → pass：稳定；
fail → pass：改进；
pass → fail：回归；
fail → fail：未解决；
metric_up_cost_up：质量提升但成本增加；
retrieval_up_generation_down：检索变好但生成变差；
faithfulness_up_relevancy_down：更忠实但答题性下降。
```

Compare report 的价值是揭示权衡。

它不只告诉系统变好还是变坏。

它还告诉：

```text id="m4vj27"
哪里变好；
哪里变坏；
是否值得保留这次改动。
```

## 10. 实验结论怎么写

实验结论不应该只写：

```text id="et9j4l"
分数提升了。
```

更好的写法是：

```text id="e5crkd"
在同一批回归问题上，本次改动提升了检索命中率；
其中多文档问题改善明显；
但平均延迟增加；
部分拒答题出现误答；
因此该改动适合保留在多文档场景，但需要继续调整拒答规则。
```

一个工程化实验结论应该包含：

```text id="rtwcu9"
实验变量；
对比对象；
问题集；
主要指标变化；
逐题变化；
收益；
代价；
失败原因；
下一步。
```

这样实验才能进入工程闭环。

---

## 11. 小结

实验变量与回归集设计的核心，是让 RAG 系统改动可比较。

基本原则是：

```text id="x51iam"
固定问题集；
明确 expected_behavior；
记录 expected_evidence；
一次实验控制一个主变量；
保留 run 配置和 trace；
比较 baseline 与 experiment；
同时看质量、延迟、成本和失败原因。
```

一句话收束：

```text id="s1i4sj"
回归集让 RAG 评估从“这次看起来不错”变成“这次改动相对上一次到底带来了什么变化”。
```
