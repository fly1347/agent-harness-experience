# RAG评估知识系统-01-检索层与证据层评估

## 1. 为什么要区分检索层和证据层

RAG 系统中，检索层和证据层很容易混在一起。

因为它们都发生在模型生成之前，都处理知识库内容。

但两者的评估对象不同。

可以先用一句话区分：

```text
检索层看：问题能不能找回相关候选。
证据层看：这些候选能不能支撑回答。
```

更细一点：

```text
检索层：question ↔ retrieved chunks
证据层：answer requirement ↔ evidence chunks
```

检索结果不自动等于证据。

一段内容可能和问题相似，但不足以支撑最终结论。

也可能目标来源被找回了，但真正回答问题的子片段没有进入 prompt。

因此，检索层和证据层分开评估，能让失败归因更清楚。

---

## 2. 检索层评估对象

检索层覆盖：

```text
query
retriever
topk
score
filter
rerank
hybrid search
query rewrite
retrieval result
```

它关注的是系统能否根据用户问题，从知识库中找回相关内容。

核心问题包括：

```text
目标来源有没有被召回；
关键片段有没有进入 topk；
相关结果是否排在前面；
topk 是否足够；
检索结果是否噪声过多；
score 是否有区分度；
多来源问题是否召回了多个来源。
```

检索层不负责最终答案。

它负责提供候选材料。

候选材料越可靠，后续证据组织和生成越有基础。

---

## 3. 检索层常见指标

检索层指标可以分为四类。

### 3.1 命中类指标

命中类指标看目标材料有没有回来。

常见包括：

```text
any_hit
full_hit
source_level_hit
chunk_level_hit
answer_bearing_chunk_hit
```

其中：

```text
any_hit：至少命中一个目标来源或目标证据；
full_hit：命中全部预期来源或证据；
source_level_hit：命中到文档来源级别；
chunk_level_hit：命中到具体片段级别；
answer_bearing_chunk_hit：命中真正承载答案的片段。
```

这类指标适合回归评估，因为它们比较直观。

### 3.2 排序类指标

排序类指标看目标内容排得靠不靠前。

常见包括：

```text
Recall@K
MRR
NDCG
top1_hit
target_rank
```

其中：

```text
Recall@K：top K 中召回了多少目标证据；
MRR：第一个正确结果排在多靠前；
NDCG：考虑相关性等级和排序位置。
```

这类指标更严格，也更依赖人工标注。

如果没有可靠的 expected evidence，排序类指标容易失真。

### 3.3 分数类指标

分数类指标观察检索信号本身。

常见包括：

```text
top1_score
topk_score_distribution
score_gap
min_score
max_score
avg_score
```

它们可以帮助判断：

```text
top1 是否明显领先；
topk 之间是否区分度很低；
相关和不相关结果是否分不开；
阈值是否有意义。
```

分数类指标不能直接证明答案质量。

它们只是检索信号。

### 3.4 多样性指标

多样性指标看检索结果是否过于集中。

常见包括：

```text
unique_source_count
duplicate_chunk_count
source_distribution
```

这类指标对多文档综合题、对比题、流程题比较重要。

如果 topk 全来自同一来源，可能会导致答案视角单一。

---

## 4. 检索层常见失败

检索层常见失败包括：

```text
retrieval_miss
source_hit_chunk_miss
topk_too_small
embedding_mismatch
query_mismatch
rerank_error
filter_error
```

含义分别是：

```text
retrieval_miss：目标来源或目标证据没有被召回；
source_hit_chunk_miss：来源命中了，但关键子片段没有命中；
topk_too_small：目标结果排在 topk 之外；
embedding_mismatch：向量表示不适合当前查询；
query_mismatch：用户问题表达和知识库表达差异较大；
rerank_error：重排后目标证据位置变差；
filter_error：过滤条件误伤了相关结果。
```

检索层失败的修复方向通常包括：

```text
增大 topk；
调整 query rewrite；
引入 hybrid search；
引入 rerank；
调整 embedding；
优化 chunk 策略；
增加相邻片段扩展；
检查过滤条件和权限字段。
```

---

## 5. 证据层评估对象

证据层位于检索和生成之间。

它覆盖：

```text
retrieved chunks
selected context
evidence packet
context assembly
sufficiency judge
missing evidence
secondary retrieval
refusal decision
```

它的核心问题是：

```text
当前材料够不够支持一次可靠回答？
```

证据层不只看“相关”。

它还要看：

```text
是否覆盖关键点；
是否存在必要来源；
是否能够支撑结论；
是否缺少比较对象；
是否缺少限制条件；
是否应该继续检索；
是否应该拒答。
```

证据层是 RAG 工程中非常重要的一层。

它决定模型看到的 context 是否足够。

---

## 6. 证据层常见指标

证据层指标可以分为四类。

### 6.1 充分性指标

```text
sufficiency_verdict
min_evidence_required
evidence_coverage_ratio
```

它们回答：

```text
这些证据够不够答？
```

例如：

```text
sufficient：证据足够；
partial：证据部分足够；
insufficient：证据不足；
not_applicable：知识库内没有可用证据。
```

### 6.2 缺口指标

```text
missing_evidence
missing_source
missing_aspect
```

它们回答：

```text
还缺什么？
```

缺口记录对后续改进很重要。

因为它能把“证据不足”具体化。

### 6.3 覆盖指标

```text
evidence_source_count
unique_source_count
evidence_packet_size
coverage_by_expected_evidence
```

它们回答：

```text
证据覆盖了多少来源和多少关键点？
```

对多文档问题尤其重要。

### 6.4 噪声指标

```text
irrelevant_context_count
context_noise_ratio
duplicate_evidence_count
```

它们回答：

```text
放进 prompt 的内容里，有多少是干扰材料？
```

噪声过多会让模型更容易答偏或忽略关键证据。

## 7. Evidence Packet 的意义

Evidence Packet 可以理解为生成前的证据包。

它通常包含：

```text
证据片段；
来源信息；
得分；
排序；
metadata；
是否满足回答要求的判断；
缺失证据说明。
```

Evidence Packet 的价值是让生成前状态显性化。

没有 Evidence Packet，系统可能只是把 topk chunks 直接塞给模型。

这样很难判断：

```text
模型到底看到了什么；
这些内容够不够；
是否应该拒答；
二次检索是否必要；
失败是检索问题还是生成问题。
```

有了 Evidence Packet，系统可以在生成前先做一次证据检查。

这也是从普通 RAG 走向可控 RAG 的关键一步。

## 8. 检索层和证据层的关系

两层之间的关系可以这样理解：

```text
检索层提供候选；
证据层筛选和判断候选；
生成层基于证据回答。
```

典型情况有四种：

### 8.1 检索命中，证据充分

这是理想情况。

```text
目标来源进入 topk；
关键片段进入 prompt；
证据足够支撑回答。
```

此时生成层主要考验模型和 prompt。

### 8.2 检索命中，证据不足

常见情况。

```text
来源找到了；
但关键片段不完整；
或者缺少另一份必要材料；
或者 topk 中噪声过多。
```

此时需要看：

```text
是否扩大 topk；
是否相邻片段扩展；
是否二次检索；
是否拒答或说明缺口。
```

### 8.3 检索未命中，证据不足

这是典型 retrieval_miss。

修复重点在检索层或上游建库层。

例如：

```text
query rewrite；
embedding；
hybrid；
rerank；
chunk 策略；
语料缺失。
```

### 8.4 检索命中，证据充分，但生成错误

此时问题转移到生成层。

可能是：

```text
prompt 约束不够；
模型能力不足；
答案格式问题；
引用绑定问题；
模型无证据扩写。
```

这种分层能帮助系统快速定位问题。

## 9. 检索与证据评估的工程取舍

严格的检索评估需要较精细的 expected evidence。

例如：

```text
每个问题应该命中哪些 source；
每个问题应该命中哪些 chunk；
哪些 chunk 是 answer-bearing chunk；
哪些来源是必要来源；
哪些来源只是辅助来源。
```

但标注越细，人工成本越高。

常见取舍是：

```text
source 级 expected evidence 用于基础回归；
chunk 级 evidence 用于关键问题和失败诊断；
answer-bearing chunk 用于重点样本；
LLM judge 用于辅助判断；
人工抽查用于确认关键结论。
```

工程项目不一定一开始就做最严格的指标。

更重要的是：

```text
指标能复跑；
口径能解释；
失败能归因；
改动能比较。
```

## 10. 检索与证据层的实验变量

常见实验变量包括：

```text
topk
score_threshold
embedding model
query rewrite
hybrid search
rerank
metadata filter
chunk_size
chunk_overlap
max_chunks_in_prompt
context truncation
evidence packet size
sufficiency judge
secondary retrieval
neighbor chunk expansion
```

这些变量可能影响：

```text
召回率；
证据覆盖；
噪声比例；
prompt 长度；
生成质量；
延迟；
成本。
```

所以做实验时不能只看一个指标。

例如：

```text
topk 增大可能提高召回，但也增加噪声和 token；
rerank 可能提高排序，但增加延迟；
相邻片段扩展可能补全证据，但也扩大 prompt；
sufficiency judge 能减少强答，但会增加调用成本。
```

评估要把收益和代价一起记录。

---

## 11. 小结

检索层和证据层是 RAG 评估的核心中段。

检索层回答：

```text
相关候选有没有被找回来？
```

证据层回答：

```text
这些候选够不够支撑回答？
```

两层分开后，错误可以更清楚地归因：

```text
没找回来：检索问题。
找回来但不够：证据问题。
证据够但答错：生成问题。
答对但引用错：引用问题。
```

一句话收束：

```text
检索层与证据层评估的价值，是把“模型没答好”拆成“材料有没有找回”和“材料是否足够支撑”两个更清楚的工程问题。
```
